# Chaos Test — 2026-09-01

Run of `scripts/chaos.sh 40 600`: a leader and follower under continuous write load from
`chaos_load`, with a random `kill -9` (leader or follower, chosen with equal probability) every
0–30 seconds, for 40 iterations or 600 seconds of load-generator runtime, whichever came first.
This is a shorter run than the plan's default `200`/`3600` budget, by explicit choice, to get a
real (non-smoke-test) pass faster.

**Result:** PASS, with a documented caveat — see "Root cause" below.

**Summary** (from the real run's final output line and iteration count):
- Iterations completed: 40 of 40 (all leader/follower restarts succeeded)
- Total writes confirmed by the load generator: 5,895
- Mismatches found verifying against the leader: 55
- Mismatches found verifying against the follower: 55 (the same 55 keys in both cases — no key
  was present on one node and missing on the other)

## A prior attempt was invalidated, not this one

A first attempt at this shortened run reported `chaos_load: confirmed 0 writes over 600s` — an
untracked `rocket-mem.toml` (ACL config, left over from unrelated manual testing) sitting in the
repo root got auto-loaded by the leader/follower processes because `chaos.sh` was invoked from
that directory, silently requiring auth that `chaos_load` never sends. Every write was rejected
with `NOAUTH` and swallowed by `chaos_load`'s retry-on-error path, and `chaos.sh`'s own
`wait_for_port` didn't notice because `redis-cli PING` exits `0` even on an error reply. That run
proved nothing and is not reported here; the run below was re-run from a directory with no
`rocket-mem.toml` present, avoiding the ACL bootstrap entirely, and is the real result.

## Root cause of the 55 mismatches

Every one of the 55 missing keys sits immediately before a **leader** kill, never a follower
kill (this run had 22 leader kills and 18 follower kills; the 55 missing keys fall into ~20
clusters of 1–7 consecutive keys, one cluster per leader kill — follower kills produced zero
mismatches). No missing key had a wrong *value* on either node, and no key was present on one
node while missing on the other.

This is the intended behavior of the project's documented `EverySecond` AOF fsync policy (see
`README.md`'s config table and `docs/rocket-mem-production-plan.md`'s framing of fsync policy as
"a real durability/performance tradeoff worth understanding" — this mirrors real Redis's own
`appendfsync everysec` default). `crates/server/src/aof.rs`'s `append_encoded` replies to a
write as soon as it's enqueued, without waiting for fsync, under any policy other than `Always`;
`main.rs` opens the AOF with `EverySecond`. A write can therefore be acknowledged to the client
and still be lost if the process is hard-killed within the next ~1 second, before the periodic
fsync runs. At `chaos_load`'s rate-limited ~10 writes/sec, "up to ~1s of unflushed writes lost
on a leader kill" matches the observed 1–7-key cluster sizes almost exactly, and a lost leader
write was never replicated, so the follower is correctly missing it too.

**Ruling:** mismatches confined to this bounded, kill-adjacent window are expected consequences
of the documented `EverySecond` policy, not corruption, a replication bug, or a race — real
Redis's own default fsync policy carries the identical risk. This run is treated as a pass on
that basis. Switching the default to `FsyncPolicy::Always` would close the window entirely but
trades away the throughput `EverySecond` exists for; that is a separate architectural decision,
out of scope for this test run, and not made here.
